# 四阶段实验方案与实现路径

> 2026-10-29阶段调整：按最新要求，原第四阶段拆为第四阶段“后台Service与流程整合”和第五阶段“Web应用与个性化聊天”。最新实施边界、接口、视觉设计与验收以同目录《第四与第五阶段细化方案.md》为准，本文保留早期四阶段规划。

本方案在《实验方案.md》的基础上细化，并按最新要求将实现划分为：**doc2md → DocBase → AGENTS.md 开发 → Service 与 B/S Web 整合**。第四阶段由原课件的两项扩展合并而来，现纳入本次计划。

以下工具选型、接口、目录、命令、参数和验收阈值均为**拟采用的实现设计**，尚未表示代码已实现、依赖已安装或模型接口已连通。课件模型名沿用原始记录；实际部署以可获得的服务为准。

## 一、整体实施顺序与阶段边界

| 阶段 | 输入 | 核心工作 | 输出 | 进入下一阶段的条件 |
|---|---|---|---|---|
| 1：doc2md | PDF、Word、PPT 原文档 | 解析正文、表格和图片，OCR/VL，保留来源 | Markdown、结构化内容块、图片、来源清单 | 三种格式样本均成功，内容与来源可人工核对 |
| 2：DocBase | 第一阶段完整产物 | 切片、三路索引、融合、精排、评估 | 持久化知识库、查询命令、证据 JSON | build/query/test 可运行，更新及重载通过验证 |
| 3：AGENTS.md | 第二阶段检索接口和证据 | 编写约定、接入 Agent、补检、综合回答与引用 | 约定文件、调用适配、问答记录、Mermaid | 无文件名问答、引用、无答案处理及原图核对通过 |
| 4：系统整合 | 前三阶段的稳定接口 | 后台监控与更新，任务运维，Web 交互 | 本地 B/S 应用、后台任务、运行记录 | 浏览器操作和目录变化均能跑通完整闭环 |

统一采用“先小样本跑通，再扩大数据量”的方式。每阶段先通过功能检验，再开展质量评估；发生质量问题时回到其所属模块处理。

建议实验数据：先选 PDF、DOCX、PPTX 各 1 份作为开发样本，再扩充到 12～20 份。旧格式 DOC/PPT 增加转换验证样本，不把对 DOCX/PPTX 的支持直接当作旧格式支持。题集采用 20 道调参题和 40 道冻结测试题，均由人工标注来源及答案要点。

## 二、先统一三个阶段交接的数据约定

### 2.1 doc2md → DocBase：结构化内容块

Markdown 用于阅读，`blocks.jsonl` 用于稳定传递来源和结构。DocBase 优先读取内容块，不依赖对 Markdown 重新猜测页码、图号。

每条内容块至少包含：

```json
{
  "schema_version": "1",
  "doc_id": "doc_001",
  "revision": "原文内容哈希",
  "block_id": "doc_001_r1_p12_b03",
  "type": "figure_description",
  "text": "图片中可确认的模块、流程与分支描述",
  "heading_path": ["第四章", "转发流程"],
  "category": "技术资料",
  "source": {
    "original_path": "原始文件路径",
    "rendered_pdf_path": "用于页码定位的PDF路径",
    "page_index": 12,
    "printed_page_label": null,
    "slide_number": null,
    "bbox": [50, 100, 500, 450],
    "figure_id": "fig_002",
    "image_path": "images/doc_001_p12_f02.png"
  },
  "status": "ok"
}
```

页序号对外统一从 1 开始，`bbox` 使用对应渲染 PDF 页面的坐标；示例数值不对应某份真实文档。纯文本块的图像字段允许为空。无法确定印刷页码或图题时保留空值，不编造。

### 2.2 DocBase → Agent：证据结果

查询返回 `query_id、index_version、results、diagnostics`；每条结果包含 `chunk_id、text、source_blocks、sources、各路排名、融合分数、精排分数`。跨页切片保留多个来源，不用一个页码代替全部出处。

空结果、模型不可用和正常命中必须能区分。不能把网络失败伪装成“资料里没有答案”。

### 2.3 Agent → Web：问答结果

返回 `question_id、status、answer、citations、mermaid、rounds_used、index_version、usage、timings`。其中 `mermaid` 可以为空；引用映射到真实 `chunk_id` 和来源；Token 统计接口未提供时记为空值，不估算为实测值。

这些约定在阶段一确定初版；后续若有变化同步升级 `schema_version`，避免最后整合时各模块输出不一致。

## 三、第一阶段：doc2md 文档解析开发

### 3.1 所需资源与工具

| 类型 | 准备内容 | 使用方式与选择理由 |
|---|---|---|
| 文档样本 | PDF、DOCX、PPTX；扫描页；带流程图和表格的页面 | 先各 1 份，再补充旧格式与复杂版式 |
| 开发环境 | Python、独立虚拟环境、Git、编辑器 | 固定项目依赖和实际版本 |
| Office 转换 | LibreOffice 命令行 | Word/PPT 转 PDF，保留可核验的页面副本 |
| PDF 解析与渲染 | PyMuPDF | 获取文字块、图片、位置及整页/区域图像 |
| OCR | Tesseract 引擎及 `chi_sim`、`eng` 语言数据 | 识别扫描页、图内文字；与 VL 各司其职 |
| 图片处理 | Pillow | 裁剪、缩放、去重和预处理 |
| 视觉模型 | 可调用图片输入的 VL 服务 | 课件记录为 Qwen3.6-27B-VL；先确认真实服务名和请求格式 |
| 来源核对 | PDF 阅读器、原文档查看工具 | 人工检查抽取结果及图片关系 |

**明确主流程：** PDF 直接解析；Office 先转 PDF，再走统一页面解析。这样矢量图、组合图形和箭头可以作为整体渲染。LibreOffice 官方支持命令行转换，PyMuPDF 官方提供页面/区域渲染与图片处理方法。[LibreOffice 参数说明](https://help.libreoffice.org/latest/en-US/text/shared/guide/start_parameters.html)、[PyMuPDF 图片处理](https://pymupdf.readthedocs.io/en/latest/recipes-images.html)

该路线的代价是原始 Word/PPT 的标题与对象结构可能丢失，因此需检查阅读顺序并恢复 Markdown 标题/表格。若特定样本效果不足，再添加原生结构解析适配，不在初版同时维护多条主流程。Word 页码以保存的渲染副本为准，并同时保留原文路径；PPT 保留幻灯片号及对应渲染页。

OCR 引擎与语言数据需要分别准备，安装 Python 包不能替代引擎安装。[Tesseract 安装说明](https://tesseract-ocr.github.io/tessdoc/Installation.html)

模型资源建议先使用可获得的推理服务。只有计划本地部署时才单独评估权重、推理框架、内存/显存及吞吐；本方案不根据模型名预设硬件必然满足。

### 3.2 具体实现流程

| 步骤 | 具体任务 | 产物/完成标志 |
|---|---|---|
| A1 输入管理 | 遍历指定文件/目录；识别类型；生成稳定文档 ID；计算哈希；排除输出目录 | 文档清单、待解析队列 |
| A2 归一化 | Office 转 PDF；每文档独立输出；检查转换返回状态、页数和可读性 | 渲染 PDF、原文与渲染副本映射 |
| A3 正文解析 | 逐页读取文字块、位置、字号、表格信息；处理多栏顺序和重复页眉页脚 | 正文/标题/表格内容块 |
| A4 OCR 补充 | 对无有效文本的扫描页做 OCR；图像文字按需要识别；与原生文字去重 | OCR 内容块、识别状态 |
| A5 图片识别 | 提取位图；对矢量、组合流程图使用区域或整页渲染；保存坐标和上下文 | 图片文件、图像块与来源 |
| A6 VL 释义 | 输入图片与附近标题；提取对象、箭头、步骤、条件和不确定项 | 结构化释义及自然语言描述 |
| A7 图文组装 | 按阅读顺序写 Markdown；图片旁插入释义；写出 block ID 和来源映射 | Markdown、blocks.jsonl、manifest.json |
| A8 批处理 | 加入进度、错误日志、超时重试；相同图片及配置复用缓存 | 可重复运行的批量解析入口 |

图片区域检测的初版可先采用“整页候选+按位置裁剪”。不能只遍历内嵌位图，因为原生流程图可能全部由形状和连线组成。整页释义应标为页面级来源；只有可靠识别到图号时才赋予具体图号。

VL 提示词建议固定输出五部分：图类型、节点与标签、有向关系、条件与例外、不清晰内容。要求依据画面描述；输出结构检查通过后再转为正文。失败时保留图像与 `failed/pending` 状态，禁止悄悄生成空释义后标记成功。

缓存键包含图片哈希、模型标识、提示词版本和解析配置版本；更换提示词后重新生成相关释义。批处理可继续完成其他文件，但必须报告成功、部分成功和失败数量。

### 3.3 预期效果

- 用户能打开 Markdown 阅读主要正文、表格、原图及图像释义。
- 流程图中的节点、连接方向、分支条件成为可检索文本。
- 图片和内容块可以定位到原文档及对应页/幻灯片，Word 可定位保存的渲染页。
- 相同配置重复运行可复用已完成结果，模型失败可单独重试。

建议产物组织：

```text
parsed/<doc_id>/<revision>/
  document.md
  blocks.jsonl
  manifest.json
  rendered.pdf
  images/
  parse.log.jsonl
```

对原始 PDF 可在 manifest 中引用保存的原文版本，不强制重复复制为 rendered.pdf。原文后续变化时，历史引用仍需绑定其对应版本。

### 3.4 检验与阶段验收

| 检验项 | 检验方法 | 通过条件 |
|---|---|---|
| 格式覆盖 | 三种开发样本逐个处理，再加入 DOC/PPT 转换样本 | 各类文件可转换/解析，或有明确失败原因；不能将失败计为成功 |
| 内容完整性 | 人工选择至少 15 页，覆盖正文、表格、扫描页 | 报告文字段落、表格及图像的遗漏和顺序错误，关键答案证据无遗漏 |
| 图像释义 | 人工标注至少 10 幅图的节点、箭头和条件 | 所有演示图无关键方向/条件错误，其他错误逐项记录 |
| 来源定位 | 抽查至少 20 个内容块，打开对应原文/渲染页 | 20/20 定位正确；页码、图像和文档一致 |
| 幂等与重试 | 相同输入连续执行两次，再模拟一次 VL 失败 | 不产生重复有效块；失败有记录；重试可补齐 |

数量为建议的阶段检查样本，不替代最终冻结测试集。若不足 10 幅图，应扩充样本或报告实际分母。

**阶段交付：** 可运行解析入口、三个格式样本产物、元数据规范、模型适配器、人工核对表、错误记录。核心来源错误未修复前不进入正式建库。

## 四、第二阶段：DocBase 知识库与混合检索开发

### 4.1 所需资源与工具

| 类型 | 准备内容 | 用途 |
|---|---|---|
| 输入数据 | 第一阶段 Markdown、blocks.jsonl、manifest 和图片释义 | 保持来源链和图文上下文 |
| 稠密编码 | Qwen3-Embedding-8B 服务/部署 | 编码文档片和查询；服务端维度、归一化及指令需确认 |
| 关键词检索 | jieba + rank_bm25 | 中文分词、术语保留和 BM25 打分 |
| 学习型稀疏编码 | BGE-M3 稀疏接口；或 FlagEmbedding 本地推理 | 获取 token ID → 权重，建立第三路索引 |
| 精排 | Qwen3-Reranker-8B 服务/部署 | 输入查询及候选，返回相关性排序 |
| 存储与计算 | SQLite、NumPy、JSON 文件 | 元数据与版本；稠密矩阵；稀疏倒排与排名 |
| 评估资源 | 人工证据标注、调参题、冻结测试题 | 检索质量评估及消融比较 |

建议初版采用 **SQLite 元数据 + NumPy 精确向量搜索 + BM25 + 稀疏倒排表**。它面向本实验的小规模文档，便于检查和复现；后续数据规模确有需要再替换向量后端。归一化向量的点积可用于余弦相似度排序，矩阵运算使用 NumPy。[NumPy dot](https://numpy.org/doc/stable/reference/generated/numpy.dot.html)

BM25 在文档和查询两侧使用相同分词器、术语词典与大小写规则；英文接口名、命令和带下划线标识符保留为完整候选词。[jieba 官方仓库](https://github.com/fxsjy/jieba)、[rank_bm25 官方仓库](https://github.com/dorianbrown/rank_bm25)

**提前确认 BGE-M3 的稀疏输出。** 官方示例通过 `return_sparse=True` 获取 `lexical_weights`。只有稠密 embedding 输出的接口不能完成这一通路；不能用 BM25 再做一次冒充 BGE 稀疏检索。[BGE-M3 模型说明](https://huggingface.co/BAAI/bge-m3)

Qwen Embedding 与 Reranker 的客户端应分别按实际服务格式适配，模型发布方给出了不同调用示例，不能假定所有模型共享同一请求结构。[Qwen3-Embedding-8B](https://huggingface.co/Qwen/Qwen3-Embedding-8B)、[Qwen3-Reranker-8B](https://huggingface.co/Qwen/Qwen3-Reranker-8B)

### 4.2 具体实现流程

**B1：数据读取与切片。** 验证 schema 和文档版本，按标题与 block 边界组织 chunk。初始目标 600 tokens、重叠约 100 tokens，尽量保持表格与图像释义完整；超长内容拆分时保留相同父块关系。用实际 tokenizer 计数，为每片保留来源块列表。

**B2：先建立稠密检索基线。** 批量编码切片，检查向量长度、数值有效性和行号对应关系。查询使用同一模型、维度和规定的编码方式，输出带来源的 Top-K，形成第一份可测基线。

**B3：加入 BM25。** 建立分词结果缓存，加入领域术语词典。通过专有名词、接口名、英文缩写题检查候选是否能出现；记录候选排名。

**B4：加入 BGE-M3 稀疏检索。** 文档和查询使用同一稀疏模型与 tokenizer，按 token ID 的共同项累计权重乘积；保存倒排表。用人工检查的小向量验证打分结果，再对真实语料检索。

**B5：RRF 融合。** 三路分别召回 30 条，先按类别和有效文档状态过滤，再按稳定 chunk ID 合并；从 1 开始排名，采用 `Σ 1/(60+rank)`。无该路召回则该项为 0。保留原始排名以便诊断。

**B6：Reranker 精排。** 融合后最多 50 条进入精排，按模型长度预算处理输入，最终返回 5 条并保留检索来源；不能把不包含在候选中的证据寄希望于精排找回。数值均为调参起点。

**B7：持久化与增量。** 对未变化内容复用编码缓存；修改文档生成新版本块；删除文档清除有效记录。小规模初版可在复用编码的基础上重建 BM25/倒排和矩阵快照，达到“增量处理输入、原子发布索引”的效果，记录索引实际重建成本，不宣称已实现全部索引的原位增量算法。

索引版本清单包含内容版本、切片参数、分词词典、模型标识/维度、schema 与创建时间。新索引在临时目录完整构建并验证后发布；当前查询始终固定一个版本。失败不覆盖旧版；模型或切片规则变化时不得混用不兼容的旧缓存。

**B8：检索评测。** 实现三种模式：`build、query、test`。分别保存逐题候选、融合、精排及指标。先用调参集确定参数，再执行冻结测试集，按名词题、语义题、图片题和综合题分别报告结果。

### 4.3 预期效果

- 不知道文件名时，也可以按内容找到相关图文证据。
- 精确术语与语义改写均有召回路径，图片语义参与检索。
- 查询输出可直接给 Agent 使用，无须 Agent 再猜测来源位置。
- 进程重启可重载知识库；增改删后索引与当前文档一致。

建议提供的 CLI 形式如下，**为待实现接口示例**：

```text
python -m docqa.docbase build --input <parsed_dir> --index <index_dir>
python -m docqa.docbase query --index <index_dir> --question "问题" --top-k 5 --format json
python -m docqa.docbase test --index <index_dir> --dataset <questions.jsonl>
```

### 4.4 检验与阶段验收

| 检验项 | 检验方法 | 通过条件 |
|---|---|---|
| 三路有效 | 分别单独执行三路查询，保存候选和模型信息 | 确认使用不同检索能力，而非三次同一结果 |
| 融合正确 | 使用已知排名的小型候选表手工计算 RRF | 计算和合并结果与人工结果一致 |
| 精排作用 | 固定同一候选集，对比精排前后的相关证据位置 | 无候选丢失/错配，报告实际排序增益或退化 |
| 来源完整 | 抽查 Top-K 的 chunk、block、页和图 | 来源字段完整且能打开对应证据 |
| 重载一致 | 保存后重启进程，再查询相同题 | 相同配置排序一致，浮点并列项采用稳定次序 |
| 增改删一致 | 新增文档；修改关键事实；移除文档；发布新索引 | 新内容可检索，旧版本和删除文档退出有效结果 |
| 检索质量 | 冻结题集计算 Hit@5、Recall@5、MRR@5 | 建议可回答题 Hit@5 ≥85%；同时报告各题型及实际分子/分母 |

证据标注采用“文档版本+页/图/段落”的稳定单元，重叠切片命中同一证据只计一次。无答案题不参加可回答题的召回指标。对照组建议依次为：稠密；稠密+BM25+RRF；三路+RRF；三路+RRF+精排。

**阶段交付：** 三种 CLI、版本化索引、统一证据 JSON、参数配置、逐题评测和增量更新报告。未拿到真实稀疏输出时可继续联调两路，但必须标注“三路检索尚未完成”。

## 五、第三阶段：AGENTS.md 与 Agent 问答开发

### 5.1 所需资源与工具

| 类型 | 准备内容 | 用途 |
|---|---|---|
| Agent 运行环境 | 能读取项目约定、执行命令/工具的 CodeAgent | 自动决定查询、执行检索和组织回答 |
| 项目约定 | AGENTS.md；必要时按所选 Agent 的规则设置入口文件 | 声明知识库和检索/引用要求 |
| 检索工具 | 第二阶段 JSON CLI，以及受控的按 ID 取证据入口 | 查询、补查上下文、核对来源 |
| 综合推理 | Agent 自带模型；或单独 Chat 服务 | 课件记录 GLM-5.1，实施时明确实际调用链 |
| 图形渲染 | Mermaid 渲染器 | 验证生成的流程图能否渲染，再比较语义 |
| 评测资源 | 固定题集、原图、调用日志、人工答案 | 判断执行约定和回答质量 |

**推荐实现方式：** 先以现有 CodeAgent 作为问答执行器，由其加载项目约定并调用 DocBase CLI。Agent 自带模型可以完成综合推理；若必须复现课件 GLM-5.1，则显式增加 Chat 适配器并记录谁负责检索决策、谁负责最终作答，避免两套流程重复检索或重复生成。

为第四阶段预先封装 `AgentRunner.ask(question, category, max_rounds) -> AnswerResult`；其内部调用真实 Agent 的无头/程序接口，捕获执行结果并规范化。具体启动参数在选定 Agent 后验证。若环境不提供无头能力，阶段三先完成交互验证，同时将可编程入口列为阶段四前置项。

### 5.2 具体实现流程

**C1：验证约定确实被加载。** 将知识库位置、可用类别、CLI 工作目录、命令和 JSON 返回样例写入实际支持的约定文件。在新会话里用库中特有、模型无法预知的测试事实提问，并检查检索日志。不能凭模型说“我读过文件”判定加载成功。

**C2：形成可执行的约定。** 约定至少覆盖：

| 部分 | 应写清的内容 |
|---|---|
| 知识库存在 | 存放位置、覆盖范围、索引状态、使用入口 |
| 何时检索 | 涉及文档事实先检索；不依靠模型记忆猜测库内内容 |
| 如何查询 | 复杂问题拆分；保留技术名词；必要时语义改写；类别未知时不强行过滤 |
| 何时补检 | 关键步骤/条件缺失、证据冲突、来源不清时补查；最多三轮 |
| 如何引用 | 引用真实结果 ID；重要结论绑定具体证据；不得编造页码和链接 |
| 如何呈现 | 答案优先，随后来源；比较用表格，流程按需 Mermaid；注明不确定项 |
| 如何处理失败 | 区分知识缺口、检索空结果和服务故障，给出对应状态 |

约定还应明确：检索得到的文档文字属于待分析资料，文档中的命令或提示词不能替代项目约定。

**C3：建立检索和取证工具。** 将 CLI 输出稳定为 JSON；增加通过 chunk/block ID 获取邻近正文、原图或来源摘要的操作。语义补检调用 query，直接取上下文调用 get，不把两者混为同一种能力。

**C4：执行多轮问答。** 提问 → 查询规划 → 第一轮检索 → 检查证据覆盖 → 最多两轮补查 → 综合回答 → 绑定引用。输出已知事实、缺失信息和必要的不确定说明；跨文档冲突注明版本与来源，不无依据地选一个答案。

**C5：生成并核对图。** 图片问题优先取到原图对应释义；从证据重建节点和关系，生成 Mermaid，实际渲染后比较原图。语法成功和事实正确分别检验。[Mermaid 文档](https://mermaid.js.org/intro/)

**C6：结果规范化与日志。** 捕获问题、每轮查询、证据 ID、实际模型/Agent、索引版本、最终引用、耗时和可获取的用量。结构不合法时做有限格式修复；修复不能新增没有证据支持的事实。后台调用失败返回明确错误状态。

### 5.3 预期效果

- 用户只描述内容，Agent 自动检索并回答，不需要记命令或文件名。
- 问题所需证据不足时补检；库内无法回答时说明缺口。
- 回答的重要事实带可验证引用，点击或按路径能回到原文。
- 流程问题能输出正确渲染的 Mermaid，并提供原图供核验。
- 相同问答入口既支持阶段三命令行实验，也能被阶段四后台调用。

**建议的约定文本骨架**（属于实验素材，不写入当前工作目录根部的实际 AGENTS.md）：

```text
知识库：填写真实索引位置、类别和查询工具。
文档事实问题：回答前先执行查询，保存证据 ID。
查询：先保留用户术语，再按缺口改写或拆分；类别不确定时全库查。
补检：缺关键条件、上下文或来源时补查，最多三轮。
引用：重要结论附真实文档、页/幻灯片、图号和证据 ID。
缺证据：说明当前证据不足；工具故障须单独说明。
流程：依据证据生成 Mermaid，附原图位置，不添加未证实关系。
输出：回答、证据引用、必要的图/表、尚未解决的问题。
```

### 5.4 检验与阶段验收

| 检验项 | 检验方法 | 通过条件 |
|---|---|---|
| 实际检索 | 新会话提问，只在库内设置的特有事实；审查工具日志 | 所有应检索演示题均先检索，不能仅口头声称已检索 |
| 无文件名提问 | 仅用自然语言询问事实或流程 | 找到正确文档，并输出来源 |
| 补检与停止 | 设置首轮不完整的多证据问题 | 触发有效补查，轮次不超限，保留新增证据 |
| 引用真实性 | 人工逐条检查关键结论和引用 | 演示引用无虚构；冻结集引用覆盖率建议≥90%，支持率另报 |
| 无答案/故障 | 分别给出无答案题、模拟接口超时 | 无答案正确拒答率建议≥80%；故障不冒充知识缺口 |
| 图文互证 | 选择至少 3 幅流程图，比较节点、边、方向和条件 | Mermaid 均可渲染；演示图无关键语义错误 |
| 约定贡献 | 同 Agent、模型、工具、索引，对比移除/加入知识库专用约定 | 报告检索执行率、回答要点、引用及成本差异 |

若运行环境内置“必须检索”的固定编排，约定消融中仍然强制调用，则不能据此声称检索行为提升来自 AGENTS.md；需要说明编排与约定各自承担的作用。

**阶段交付：** 实际 Agent 约定文件、检索工具说明、AgentRunner 适配、结构化问答结果、调用日志、两类核心演示、评估报告。

## 六、第四阶段：后台 Service 与 B/S Web 系统整合

### 6.1 所需资源与工具

| 类型 | 准备内容 | 用途 |
|---|---|---|
| 模块依赖 | doc2md、DocBase、AgentRunner 的已验收接口 | 直接复用前三阶段能力 |
| 后端 | FastAPI、ASGI 服务运行器 | HTTP API、静态页面、任务和文件访问入口 |
| 任务存储 | SQLite 任务表与运行日志 | 持久化任务、查询状态、重启恢复 |
| 调度/监控 | Python 定时扫描、文件哈希、目录配置 | 初版周期扫描即可实现目录自动更新 |
| 前端 | HTML/CSS/JavaScript、浏览器、Mermaid | 文档/任务管理、问答、图形与来源展示 |
| Agent 调用 | 阶段三无头/程序接口 | 后台执行问答，无需用户操作命令行 |
| 运行环境 | 本地服务进程；可按需要配置系统自启动 | 初版单机、单用户，保存数据目录和配置 |

**建议实现：** 同一 FastAPI 应用提供 API 与静态页面；浏览器通过 HTTP 操作，形成 B/S 架构。前端先采用原生页面，任务进度用轮询；后续再按实际需要引入框架和流式响应。FastAPI 官方提供 API、静态文件及生命周期管理方式。[FastAPI 教程](https://fastapi.tiangolo.com/tutorial/)、[静态文件](https://fastapi.tiangolo.com/tutorial/static-files/)、[Lifespan](https://fastapi.tiangolo.com/advanced/events/)

初版约定单服务实例、单个索引构建 worker；长耗时解析/模型调用交给独立 worker，不阻塞 HTTP 请求。持久化任务表承担恢复依据，不能仅以进程内列表或一次 HTTP 请求后的临时后台任务充当可靠队列。

### 6.2 后台 Service 实现流程

| 步骤 | 工作内容 | 关键实现要求 |
|---|---|---|
| D1 服务接入 | 为解析、建库、问答、取来源封装统一调用 | API 层编排，不重新实现前三阶段算法 |
| D2 目录注册 | 设置目录、类别、递归、类型、扫描周期 | 监控目录与输出目录分离，保存配置 |
| D3 变化检测 | 扫描新增/修改/删除文件，比较哈希 | 等文件写入稳定再解析，连续变化合并 |
| D4 创建任务 | 记录任务类型、对象版本、状态、重试次数 | 幂等键防重复，同文档串行处理 |
| D5 执行更新 | doc2md → 更新清单 → DocBase 构建新快照 → 发布 | 更新成功才切换，失败保留旧索引和诊断 |
| D6 运行维护 | 显示队列、进度、失败详情、手动重试和暂停监控 | 错误可定位到文件、阶段和模型调用 |
| D7 恢复与启动 | 服务启动时检查未完成任务和索引完整性 | 中断任务标记待恢复，验证后重试，避免重复发布 |

建议任务状态：`queued → running → succeeded / failed`，另设 `interrupted` 表示退出中断，重试回到 queued；进度同时报告“当前阶段、完成数量、总数量”，不知道总量时不显示假百分比。

索引构建采用写入锁，查询固定快照版本；构建中的新索引不可被查询。首次建库未完成时显示“知识库未就绪”，而不是返回“没有找到资料”。删除源文件后，对新查询立即过滤失效文档，再在下一快照中移除；源目录暂时不可访问时不把所有文件误判为删除。

建议初始扫描周期 30 秒，参数化配置。手动更新与自动扫描共用同一队列。对图像/VL 和编码复用前三阶段缓存；新增文件、更新文件和失败重试均有可见记录。系统自启动可在人工启动和停止验证通过后再配置。

### 6.3 B/S Web 实现流程

页面划分为四个功能区：

| 页面/功能区 | 用户操作 | 显示结果 |
|---|---|---|
| 文档与监控 | 注册目录、选择类型/类别、手动解析或更新、重试失败文件 | 文档状态、版本、最近处理时间、监控开关 |
| 任务与运行状态 | 查看任务、错误详情与重试 | 排队/执行/成功/失败、阶段进度、服务和模型可用状态 |
| 智能问答 | 输入问题、可选类别、提交、查看会话 | 回答、引用、Mermaid、耗时与可获得的用量 |
| 原文与图像 | 点击来源、查看原图和对应渲染页 | 文档名、页/幻灯片、原图、图像释义及原文件下载入口 |

**浏览器问答链路：** 提交问题 → 后台写入问答任务并立即返回任务 ID → 浏览器轮询状态 → AgentRunner 检索与回答 → 保存结果 → 浏览器渲染回答、图形和引用。

来源访问通过 doc_id、revision、page、figure_id 等已登记标识解析，不让浏览器直接读取本机任意文件路径。优先提供渲染 PDF 页链接及图像预览；原始 Word/PPT 提供下载或打开入口，不假设浏览器能直接在线渲染 Office。历史回答引用绑定历史文档版本，不能指向内容已变化的同名文件。

问答正文和 Mermaid 渲染限制为项目允许的格式，文档内容不作为任意 HTML 执行。初版服务绑定本机地址；若后续扩展多人访问，再补账号与访问范围管理。

### 6.4 建议 API 契约

| API | 用途 | 主要返回值 |
|---|---|---|
| `POST /api/watches` | 注册监控目录 | watch_id、有效配置 |
| `PATCH /api/watches/{id}` | 暂停/恢复、调整周期 | 最新监控状态 |
| `GET /api/documents` | 文档清单 | doc_id、revision、类别、处理状态 |
| `POST /api/documents/{id}/refresh` | 重解析指定文档 | task_id |
| `POST /api/index/build` | 手动建库/更新 | task_id |
| `POST /api/questions` | 提交问答 | question_id、task_id |
| `GET /api/tasks/{id}` | 查询进度/错误 | status、stage、progress、error |
| `POST /api/tasks/{id}/retry` | 重试失败/中断任务 | task_id |
| `GET /api/questions/{id}` | 读取答案 | AnswerResult |
| `GET /api/sources/{doc_id}` | 读取已登记的指定版本来源 | PDF/图片/元数据；版本、页、图通过参数选择 |
| `GET /api/health` | 运行状态 | 服务、当前索引、worker 状态 |

异步任务提交成功建议返回 HTTP 202；任务失败仍可查询失败详情。API 超时、任务失败、无检索结果和无答案分别表示。任务表同时记录创建时间、开始时间、结束时间、尝试次数与 request_id，方便追踪。

### 6.5 预期效果

- 用户通过浏览器完成文档管理、提问、查看流程图和定位原文。
- 指定目录出现新文档或内容变化后，后台自动完成解析与索引更新。
- 处理失败有状态和原因，可以重试；服务重启后已完成资料与任务记录仍在。
- 正在更新索引时，用户仍可查询上一完整版本，回答标明使用版本。
- 系统可查看文档数、任务状态、问答耗时、错误数和接口提供的 Token 使用量。

### 6.6 整合检验与阶段验收

| 用例 | 操作 | 通过条件 |
|---|---|---|
| 首次运行 | 空知识库启动，注册包含三类样本的目录 | 显示未就绪→排队→解析→建库→就绪，状态真实 |
| 自动新增 | 放入新文档，不点击手动更新 | 在扫描周期加实际处理时间内可检索，记录各段耗时 |
| 自动修改 | 修改某文档的一个可验证事实 | 新版本回答正确，旧版本不进入新查询；历史引用仍可解释 |
| 自动删除 | 移出监控文档后重新问其独有内容 | 新查询不再引用失效文档；不可达目录不误触发全量删除 |
| 并发访问 | 建库期间提交多个问答 | API 不被长任务阻塞，查询固定完整索引或排队，不读半成品 |
| 失败恢复 | 模拟 VL/Embedding/Agent 超时，随后恢复服务并重试 | 错误可见，重试能完成，不产生重复有效文档/索引 |
| 重启恢复 | 在任务执行中退出并重新启动 | 旧索引仍可用，中断任务可恢复，已完成任务不丢失 |
| 浏览器问答 | 不提供文件名，只输入内容问题 | 展示正确答案、引用和对应原文 |
| 图文互证 | 在网页提出流程问题 | Mermaid 能渲染，可打开原图并核对节点、方向和条件 |
| 来源访问 | 点击 PDF、Word、PPT 来源及图像 | 定位对应版本/页/幻灯片，无错配或失效的伪链接 |

建议至少保存一次新增→自动建库→浏览器提问→图形展示→来源打开的完整演示记录。系统性能以本机与真实模型服务实测为准，分别报告扫描等待、解析、建库、检索和回答耗时，不将所有延迟混成模型耗时。

**阶段交付：** 可启动的本地 B/S 应用、API 文档、监控配置、任务与日志存储、重启恢复说明、部署/启动/停止说明、端到端验收记录。

## 七、建议工程结构与开发任务顺序

```text
docqa/
  contracts/       # Block、Chunk、Evidence、AnswerResult、Task 等模型
  model_clients/  # VL、Embedding、Sparse、Reranker、可选 Chat 适配
  doc2md/         # 转换、页面解析、OCR、图片、VL 释义、组装、CLI
  docbase/        # 切片、三路检索、融合、精排、快照、评估、CLI
  agent/          # AgentRunner、检索工具、结果规范化、日志
  service/        # 目录扫描、任务队列、worker、增量调度、恢复
  web/            # FastAPI 入口、路由、静态页面和资源
  configs/        # 示例配置；真实密钥从环境读取
  tests/          # 小型固定样本与必要的模块/整合检验
  eval/           # 调参/测试题、标准证据和评估脚本
  reports/        # 各阶段核对表、逐题结果、运行与失败分析
  data/           # 原文快照、解析产物、索引、SQLite、日志分区
  AGENTS.md       # 按选定 Agent 实际加载规则设置
```

推荐任务次序：

1. 确定输入样本、schema、来源定位规则与模型接口连通性。
2. 实现 PDF 主流程，再打通 Office 转换和 OCR。
3. 加入图像释义、图文组装及批处理，完成阶段一核对。
4. 实现带来源的稠密检索基线，再逐项加入 BM25、BGE 稀疏、RRF 与精排。
5. 完成索引快照、增量处理、CLI 和检索评估，验收阶段二。
6. 验证 Agent 约定加载；接入真实检索工具；完善补检、引用和图形输出。
7. 封装 AgentRunner 并完成问答评估，验收阶段三。
8. 接入后台持久任务、目录扫描和恢复，再开发文档/任务/问答/来源页面。
9. 执行第四阶段端到端用例，保存性能数据、演示和部署说明。

前三阶段验证各模块正确性，第四阶段集中验证自动运行、浏览器可用性和跨模块一致性。最终应能演示：**文件进入指定目录 → 自动解析图文 → 更新知识库 → 用户在浏览器提问 → Agent 检索回答 → 展示图形并定位原文**。
